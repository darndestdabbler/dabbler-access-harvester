1. Boundness vs. named saved-object resolution

Yes. The fix correctly separates two distinct questions that were previously conflated:

- “Is this form/report bound at all?”
- “Does its RecordSource resolve to a named saved table/query object?”

Using `!string.IsNullOrWhiteSpace(form.RecordSource)` and `!string.IsNullOrWhiteSpace(report.RecordSource)` for boundness is the right semantic test. In Access, a form or report can be bound by:
- a table name,
- a saved query name,
- or an inline SQL statement.

Only the first two are named saved objects. Inline SQL is still a valid bound `RecordSource`, so the prior dependence on `index.RecordSourceByObject` for boundness was incorrect. The new structure fixes that by making:

- `hasRecordSource` = “bound to something”
- `rs` from `RecordSourceByObject` = “bound to a named saved object we can identify”

That is exactly the separation the strategy needs. It also cleanly fixes the analogous report problem, because reports should be considered bound whenever `RecordSource` is non-empty, regardless of whether that source is named or inline SQL.

The new form logic is especially important because it prevents a false downgrade from “bound but unnamed source” into the same bucket as truly unbound forms. Conceptually, `hasRecordSource && rs == null` now means “bound, but source identity is not available as a named object,” which is the correct intermediate state for downstream classification.

2. Appropriateness of `MainDataEntry` at 0.60 for inline-SQL-bound forms

Yes. This fallback classification is appropriate and appears consistent with the strategy’s confidence structure.

Why it fits:

- A bound form is materially different from an unbound/navigation form. Even without a named saved source, the presence of a non-empty `RecordSource` is strong evidence that the form is used to display or edit data.
- At the same time, inline SQL removes several stronger signals the classifier can use for higher-confidence decisions:
  - no reliable named source to test for FK-child transactional behavior,
  - no direct lookup-table/source identification,
  - no saved-object lineage for richer dependency evidence.

Because of that lost specificity, assigning `MainDataEntry` but at lower confidence than the named-source transactional cases is the right tradeoff.

The chosen score also makes sense relative to the existing rule ladder you described:

- `0.85` for transactional named source + CRUD handlers
- `0.65` for transactional named source
- `0.60` for bound via inline SQL / no named-source resolution

That ordering is coherent. The inline-SQL case is weaker than a positively identified transactional source, so it should not equal or exceed `0.65`; but it is still materially stronger than “unbound” or purely navigational evidence, so it should not fall out of `MainDataEntry` entirely. The new regression test supports the intended behavioral correction: the form is no longer misclassified as unbound simply because its source is inline SQL.

Overall: the fix does correctly separate boundness from named-object resolution, and the `MainDataEntry` fallback at `0.60` is an appropriate conservative classification under the stated strategy.
