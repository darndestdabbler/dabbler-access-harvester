R1. The `NavigationGraph.TargetName` join fix in §5.7 is real and the corrected join key matches the shipped golden: forms and reports are joined by `Spec.SourceFormName`, reports do reuse that same key, and there is no top-level `Name` on `Forms` / `Reports`. I verified that directly against the current HomeHealthCare golden. The problem is that the companion §4 correction introduced a new inaccuracy while fixing the old one. It now says `Forms` entries are `{ Spec }` and `Reports` entries are `{ Spec, ParserOutput }`, but the actual manifest shape is optional on both: forms with no code-behind can be `{ Spec }`, while forms with code-behind are `{ Spec, ParserOutput }` just like reports. In the current golden, `frmBudgetServicePlan`, `frmClientDetail`, and `frmClientSearch` all ship as `{ Spec, ParserOutput }`. So the name-field part of R1 is fixed, but the revised per-category shape text is still not fully accurate.

R2. The new `VBA_RESOLVE_FAILURE` bullet in §4 is accurate as a consumer guard and is sufficient for the latent state it documents. It correctly explains the asymmetry: a module can parse and build scope, fail during reference resolution, ship as a `ParserOutput=null` stub, and still leave already-built public declarations visible to siblings under the shared `ProjectScope`. The guide also avoids overstating current impact by noting this is not observed on HomeHealthCare today and is tracked as DW-12. As documentation for a latent-but-permitted degradation contract, this looks good.

R3. The deferred-work entry itself is honest and strong. `docs/planning/deferred-work.md` DW-11 captures the defect, the proven GPT reproducer (`Optional ByVal x As Variant = MissingThing`), the double-emit constraint, and a focused owning set. The guide disclosure, however, is only partially honest. The first half of the §6 caveat is correct: `unresolved-items.json` is procedure-body-scoped because it is built from `FunctionClassification.UnresolvedReferences`, and it will miss unresolved references in procedure headers such as optional-parameter default expressions. But the final sentence overclaims: it says the per-reference fields on `ParserOutput.Body.References[]` are the authoritative, complete signal and that they capture header and module-level references the run-wide index omits. That is not true for module-level unresolved references.

The current code explicitly drops module-level references before manifest projection. `ParserOutputProjector.GroupReferencesByProcedure(...)` groups only references with an enclosing `ProcedureScope` and its own comment says module-level references are dropped because the schema has no module-level item type. I verified the effect with a direct scratch probe against the current assemblies using:

`Public Const DemoConst = MissingThing`

plus a trivial procedure body. The raw `ResolvedModule` contained one unresolved reference, but `ParserOutput.Body.References[]` contained zero unresolved references and `UnresolvedItemAggregator.Build(...)` also returned zero items. So the current manifest has no complete signal for module-level unresolved references at all. The DW-11 deferral is acceptable, but the guide still lets a consumer over-trust the manifest by claiming completeness where there is none.
