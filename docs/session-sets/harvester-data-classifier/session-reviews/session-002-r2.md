1. **R1 #1 fix — lookup-reference promotion.** The new post-pass in `AccessHarvester.Pipeline/Classification/HeuristicsEngine.cs` does fix the original “category never emitted” defect for the simplest case: once `ClassifyTable` returns `lookupGuess == true` and `TableHint.LookupReference`, the loop promotes eligible payload columns to `ColumnCategory.LookupReference`. It explicitly leaves PKs, FKs, memo columns, recurring system/audit columns, and already-PII columns alone, because it skips `IsPrimaryKey`, `IsForeignKey`, `IsMemo`, skips anything in `systemColumnSet`, and only promotes columns whose current category is `GenericNonSensitive` or `BusinessNaturalKey`. In practice, though, that last gate means the promotion is narrower than the fix description says. A non-key, non-system, non-PII lookup payload column that got classified as `SensitiveNonPii` solely because `ValueFormatDetector` found a stable shape will **not** be promoted. That is a real edge case, not a contrived one: fixed-width code tables are common in lookup/reference data, and they now stay `sensitive-non-pii` instead of `lookup-reference`. Also, the `BusinessNaturalKey` branch is effectively dead here because `ClassifyColumn` only assigns that category to non-autonumber PKs, and the post-pass already skips PKs. So the R1 fix is only partially complete: it works for plain description-text payloads, but it still misses structured lookup-code payloads. Borderline 2–3 column lookup tables do get the post-pass once the table-level hint is `LookupReference`; junction-only tables do not. The missing coverage is exactly the edge case you called out: there is no test pin for a lookup table whose payload column has a recognized non-PII format pattern.

2. **R1 #2 fix — DAO RCW release.** This one is materially fixed. Walking `OleDbDaoSchemaReader.ReadDaoAugmentations` end-to-end: `currentDbObj` and `tableDefsObj` are acquired in the outer scope and released in the outer `finally`; each `td` is acquired inside the table loop and released in its paired `finally`; each `fieldsObj` is acquired inside the table block and released in its paired `finally`; each `fd` is acquired inside the field loop and released in its paired `finally`; and both `TryReadBoolProperty` and `TryReadStringProperty` now acquire `propsObj`/`propObj` and release both in paired `finally` blocks. I do not see an unpaired acquisition among the RCWs named in the R1 finding. The inner `catch` blocks do keep iteration going, and because the releases are in `finally`, a per-field or per-table failure does not skip RCW cleanup. The `app`/`session` ownership is still delegated to `AccessComSession`, which is appropriate for the top-level Access application lifetime. So I would treat R1 #2 as resolved.

3. **R1 #3 fix — identifier escaping + narrowed catches.** `OleDbValueSampler.EscapeIdentifier` itself is fine for bracketed Access SQL. Rejecting `]` is the critical part; `NUL`, `CR`, and `LF` are sensible extra rejects; `[` and other punctuation are safe inside `[...]`. The per-query catch structure is also much better than R1: row-count, null-count, cardinality, and value-sample query failures now become `DegradationKind.SamplingError`, and the per-row catch in `SampleValues` is narrowed to `InvalidOperationException`, which is narrow enough because anything else bubbles to the outer query-level degradation path instead of being silently swallowed. The remaining problem is placement: `EscapeIdentifier(table.Name)` and `EscapeIdentifier(col.Name)` are called **outside** the surrounding `try` blocks in `SampleCore`. That means an unsafe identifier does not surface as a `SamplingError`; it throws `ArgumentException` out of the sampler and aborts the classify run. So the “surface failures as degradations” part of the fix is incomplete. Genuine query-construction failures caused by rejected identifiers are still fatal, not degraded.

4. **R1 #4 fix — property reader narrowing.** Narrowing from `catch (Exception)` to `catch (COMException)` is an improvement, and the new `finally` releases on `propsObj`/`propObj` are correct. It is also true that a missing DAO property typically shows up as a COM failure, so `COMException` is the right family. The remaining issue is that the code catches **all** `COMException`, not just the specific DAO “property not found” HRESULT. So type-conversion faults are no longer masked, which is good, but real COM/DAO access faults during property retrieval can still be silently treated as “property absent.” In other words: the fix reduced the blast radius, but it did not fully distinguish “optional property missing” from “DAO property access genuinely failed.” I would treat this as a small remaining defect rather than a blocker on its own.

5. **R1 #5 fix — implicit-FK resolver + degradations channel.** The core R1 issue is fixed. `ResolveImplicitFk` no longer fabricates `fkTarget.column = "*"`. For a bare simple table name it resolves to that table’s single-column PK; for no-PK and composite-PK targets it emits `UnresolvedImplicitFk` and returns `null`; and for more complex RowSources it degrades instead of inventing metadata. The degradation messages are clear and actionable. `ClassificationRunner` does correctly aggregate degradations from both the schema reader and the value sampler, and `ClassifyCommand` does correctly return exit code `3` and include the full degradation list in `--json-status` while only truncating the human-readable stderr preview. The one new risk area here is `DetectCompositeFks`: when `FK_NAME` is missing, it falls back to grouping on `"{FkTable}->{PkTable}"`, which is too coarse. Two separate single-column FKs from the same source table to the same target table would be conflated and falsely reported as a composite FK. I do not see tests covering that path. So the degradations channel is now real and threaded correctly, but the composite-FK detector has an edge-case false-positive.

6. **Re-check of the original concerns from R1.** Schema conformance still looks good: `ClassificationWriter` was not broken by the lookup-promotion change, and `lookup-reference` is already a valid enum in the Session 1 schema. The existing schema-validation test still gives good confidence here. The privacy invariant is also still intact: neither `classification.json` nor the new degradation/status surfaces carry raw sampled row values. `SamplingError.Detail` comes from exceptions on generated SQL that contains only identifiers, not row contents. `ResolveImplicitFk` may echo a `RowSource` string, but that is schema metadata, not sampled data. On heuristics correctness, the scanner is better than R1 overall: lookup-reference is now emitted, implicit FKs no longer invent bogus target columns, and degradations are surfaced. The two remaining heuristic correctness concerns are the lookup-code payload gap in point 1 and the unchanged ambiguity around junction-ish thin tables, which predates the R1 fixes.

7. **Anything else before closeout.** I would not close this round yet. The concrete blockers are: the lookup-promotion logic still misses fixed-format non-PII lookup payloads; the unsafe-identifier rejection path in `OleDbValueSampler` still aborts instead of degrading; and the DAO property readers still swallow all `COMException`. Beyond that, test coverage is still thin on the new code paths: there is no direct test for `DetectCompositeFks`, no direct test for `ResolveImplicitFk`’s no-PK/composite-PK branches, no test proving rejected identifiers become `SamplingError` degradations, and no test for the lookup-promotion format-pattern case. R1 #2 is resolved, and most of R1 #5 is resolved, but R1 #1, #3, and #4 are not fully closed.
