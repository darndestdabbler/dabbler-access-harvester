Step 2 — CliInvoker teardown simplification: this change is directionally correct, technically sound, and better aligned with Session 1’s exact-PID COM cleanup model than the prior behavior. The key correctness point is the architectural one the orchestrator called out: Access launched through COM here is a DCOM LocalServer, not a child in the CLI’s process tree. That means any `taskkill /PID <cli> /T /F` tree kill could terminate the CLI, but could never be relied on to reap the corresponding `msaccess.exe`. Because of that, the real guarantee must come from allowing the CLI process to execute its own `AccessComSession.Dispose()`, and Session 1 already hardened that dispose path to do graceful Quit, RCW release, double GC/finalizer drain, bounded wait, and exact-PID force kill. Session 2’s change now gives that logic a chance to run in the out-of-process report-baseline path instead of immediately killing the CLI as soon as files stabilize. That is the correct design.

The specific code path in `RunUntilFilesExist` is also sensible. Once the required files exist and their sizes are stable across multiple polls, the harness now waits up to 15 seconds for the CLI to exit naturally. That grace window is longer than the in-process 5-second exact-PID wait in `AccessComSession`, so under the expected cleanup path the CLI should have ample time to finish COM teardown and exit on its own. If it does exit, the code returns the real exit code and drained output, which is strictly better than the prior immediate-kill behavior. If it does not exit, the fallback is now a managed, PID-scoped `Process.Kill(entireProcessTree: true)` on the CLI process only, with no external `taskkill` subprocess. That fallback cannot touch unrelated Access instances, and it removes an unnecessary shell-out from test cleanup.

Most importantly, this change does preserve the intended no-orphan behavior for the report-baseline path in the normal and expected case: files stabilize, CLI keeps running only because COM cleanup is still in flight, harness waits, CLI reaches `Dispose()`, and `AccessComSession` reaps the exact Access PID it created. That is a real improvement over the previous logic, which killed the CLI immediately after files stabilized and therefore maximized the chance of aborting cleanup before the exact-PID reaper ran.

There is one subtle limitation, but I do not classify it as a Session 2 defect because it is architectural and pre-existing rather than a regression introduced here: if the CLI becomes wedged before or inside `AccessComSession.Dispose()` and is still stuck after the 15-second grace, the harness’s last-resort kill can only kill the CLI, not the DCOM-hosted Access server. In that pathological case, an orphan would still be possible. But the old tree-kill could not solve that either, and this new logic is strictly better because it gives the in-process exact-PID cleanup the best available chance to run. The empirical process-census result of zero surviving `msaccess.exe` and zero leaked `testhost` after the full tier is strong evidence that the new behavior works for the actual fragile path it was introduced to protect. I do not see a new zombie/orphan regression in this change.
