C7. I could not make the original shared-`ProjectScope` contamination finding true against the current code. `ScopeBuildingVisitor.BuildModuleScope` does attach the `ModuleScope` to the shared `ProjectScope` before it walks the module body, but the expected post-attach throw vectors are not there. `Scope.AddDeclaration` is append-only and does not reject duplicates, so there is no duplicate-symbol or name-collision throw during registration. Inside `ScopeBuildingVisitor`, the only non-argument throw sites after attachment are the `LocalDeclarationStatement` / `LocalConstantStatement` guards that fire when `CurrentProcedureScope` is null. On parser-produced input those nodes are visited only after `EnterProcedure(...)` has pushed a `ProcedureScope`, and they cannot appear directly in `Module.Items` because they are statements, not module items. I also checked the resolver side: `ReferenceResolver.ResolveModule` / `Resolve` have no throw sites beyond null-argument guards. So the original A1 theory still lacks a concrete parser-producible counterexample. On A2, the pipeline now explicitly documents its choice: if a module ever reached the per-module `VBA_RESOLVE_FAILURE` catch, the already-built public declarations would remain sibling-visible. That is a semantics choice, not accidental leakage. I could not identify a live resolver throw path that makes this state reachable in the current repo, so I would not reopen C7 as a shipped code defect.

C8. The name-divergence concern does not survive a direct read of the extractor and registry contracts. For forms and reports, `FormMetadataExtractor` / `ReportMetadataExtractor` do not read a top-level `Name` field from the IR JSON at all; they take the object name as an explicit argument derived from the `ir/<Category>/<name>.ir.json` file stem and set `Name = name`. `BuildAccessObjectModelRegistry` reads those same IR file names and feeds `AccessObjectModelRegistry`, which prebuilds dual-key indexes by both `Name` and `ModuleName`. `ReferenceResolver` then asks the registry to resolve controls using `owningClass.Name`, so the by-`Name` path is structural here, not accidental: file stem and metadata `Name` are the same value by construction. The only real divergence class left is `ModuleName != Name`, and the new hermetic pin in `tests/AccessHarvester.Tests/ManifestResolverWiringTests.cs` covers exactly that case (`Form_TotallyDifferent` module name with `frmDiverge` file/form name) and proves the by-`Name` fallback works. I also did not find a separate sanitization step on form/report IR file names that would create a silent mismatch at this layer; an illegal filesystem name would fail earlier in extraction rather than become a different lookup key. So I would not reopen C8.

C9. Here the contrarian hypothesis is true, and it is a real code defect, not just a missing proof. The key mismatch is structural. `ReferenceResolver.WalkProcedure(...)` visits procedure parameters before it visits the body, and `AstChildren` confirms that a `Parameter` node exposes both `Type` and `DefaultValue` as children. `ParserOutputProjector.GroupReferencesByProcedure(...)` then groups every resolved reference whose enclosing scope has a `ProcedureScope`; it does not limit that set to body-only references. `FunctionClassificationBuilder`, by contrast, deliberately walks only `procedureAst.Body` and explicitly skips the header because it does not want parameter/type-header concerns to affect side-effect classification. That means unresolved references in procedure headers can appear in `ParserOutput.Body.References[]` without ever entering `FunctionClassification.UnresolvedReferences`, and `UnresolvedItemAggregator.Build(...)` currently depends on the latter plus navigation targets only.

I verified that mismatch directly with a scratch probe against the current assemblies using this legal parser-produced input:

`Public Sub Demo(Optional ByVal x As Variant = MissingThing)`

with a trivial body. The projected parser output contained one unresolved reference (`MissingThing`, reason `not-in-scope`) in `Body.References`, while `FunctionClassification.UnresolvedReferences` for the same procedure was `0` and `UnresolvedItemAggregator.Build(functionClassifications: classifications)` returned `0` items. So `unresolved-items.json` is not a structural superset of parser-output unresolved references; it only happens to reconcile on HomeHealthCare because that corpus does not exercise this header-level case. The interpretation guide's current wording in section 6 also understates this: it says the run-wide index aggregates the per-procedure unresolved references that the function-classification pass collected, but it does not warn that unresolved header/default-value references are excluded. C9 should therefore be reopened as a Major code defect with a secondary documentation gap.
