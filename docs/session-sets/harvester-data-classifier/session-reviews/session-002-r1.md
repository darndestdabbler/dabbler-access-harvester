1. Schema conformance. Structurally, the emitted JSON shape from `ClassificationWriter` is aligned with the Session 1 Draft-07 schema. At the root it always writes `version`, `database`, `scannedUtc`, `config`, and `tables`. At table level it writes every required field: `name`, `isLinkedTable`, `rowCount`, `lookupGuess`, `nonKeyNonSystemColumnCount`, `referencedByFkCount`, `tableHint`, `confidence`, `firedHeuristics`, `humanOverride`, and `columns`. At column level it likewise writes the full required set, including the scanner-default `humanOverride` object. The category and hint wire names are correctly kebab-case because `ColumnCategoryWire.ToWire()` maps to the exact schema enums such as `surrogate-autonumber-pk`, `foreign-key`, `generic-non-sensitive`, and `entity-pii-bearing`. The FK-authority `allOf`/`if`/`then` constraint is satisfied by scanner output because FK columns still emit `humanOverride.category = null` and `humanOverride.maskingStrategy = null`, which are explicitly permitted by the schema for FK columns. `valueFormatPattern` conformance is enforced indirectly by the scanner path: `OleDbValueSampler` gets patterns only from `ValueFormatDetector`, and that detector uses the same structural rules as the schema—only `A-Z`, `#`, `?`, and allowed separators, plus a required `[#?]` placeholder. There is also a schema-validation unit test, `Writer_output_validates_against_classification_schema`, that evaluates actual writer output against the committed schema. So I do not see a root writer/schema mismatch. The caveat is only that the writer itself does not revalidate `ValueFormatPattern`; conformance currently depends on the scanner pipeline supplying a valid pattern.

2. Privacy invariant (plan § 4). On the scanner path, I do not see raw sampled values being written into `classification.json`. The only place live data values exist is inside `OleDbValueSampler.Sample`. `SampleValues` materializes them into a local in-memory list, but that list is immediately reduced to derived signals: `piiValueMatch` is computed as a boolean by regex checks, and `valueFormatPattern` is computed by `ValueFormatDetector`. `ColumnStatistics` contains only `RowCount`, `NullCount`, `Cardinality`, `PiiValueMatch`, and `ValueFormatPattern`; it has no field for raw exemplars. `HeuristicsEngine` consumes only those derived statistics, and `ClassificationWriter` serializes only those derived fields plus empty-string scanner defaults for `notes`. The CLI `--json-status` envelope also carries only counts, paths, excluded tables, and degradations. So within scanner scope, raw sampled values do not have a serialization path into the emitted JSON. Reviewer-authored `notes` are correctly out of scope here. The only nuance is that `valueFormatPattern` can preserve literal uppercase prefixes such as `MRN-#######`, but that is still a derived format pattern of the kind the schema explicitly allows, not a raw sampled value.

3. Heuristics correctness vs. the plan. The lookup-table tiering from § 3.1 is implemented correctly at table level: `CountNonKeyNonSystem` excludes PKs, FKs, and recurring system columns, and `ClassifyTable` maps `1` remaining column to a strong lookup guess, `2` or `3` to a weaker lookup guess, and larger shapes away from lookup. System/audit detection from § 3.2 is also implemented correctly: `BuildSystemColumnSet` requires both a configured name match and recurrence of that exact column name across multiple tables. PII detection from § 3.3 is broadly faithful: a name match and/or sampled-value match can elevate a column to PII, and `tablePiiObserved` enforces the lookup veto so thin PII-bearing tables do not get treated as safe reference data. The Jet/ACE requirements from § 8 are mostly met: `SafeCardinality` uses the required subquery form instead of `COUNT(DISTINCT)`, the reader probes ACE 16.0 then 12.0 and fails loudly if unavailable, DAO is used for AutoNumber and lookup RowSource recovery, and `MSys*` tables are excluded.
   
   The major miss is the ten-category column taxonomy from § 3.5. `HeuristicsEngine.ClassifyColumn` never emits `ColumnCategory.LookupReference` at all. Even when a table is correctly guessed as a lookup/reference table, its non-key payload columns remain `generic-non-sensitive` unless a human manually corrects them later. Because the contract says per-column category is authoritative downstream, that is not just a labeling quirk; it undermines the preserve behavior the plan associates with lookup/reference data. A second, narrower miss is in implicit FK recovery: `ReadLookupRowSource` does recover some lookup FKs, but when the RowSource is a bare table name it emits `fkTarget.column = "*"`, which is schema-valid as a string but not actually authoritative FK metadata.

4. Resource hygiene around COM. The COM release pattern is only partially sound. The inner `TableDef` and `Field` RCWs are at least wrapped in `try/finally` with `Marshal.ReleaseComObject`, which is the right basic pattern and means those two high-frequency objects are not leaked on the simple success path. But the outer DAO objects are not managed with the same rigor: `currentDb`, `tableDefs`, each `fields` collection, and each `field.Properties` collection are acquired as RCWs and never released in corresponding `finally` blocks. That means there are still COM references that can survive both normal completion and exceptions. I agree that `GC.Collect()` should not be required if `AccessComSession` owns and disposes the Access application, but the present implementation still relies too much on that outer disposal to clean up child RCWs it explicitly created. So I would not sign off this as fully sound COM hygiene.

5. Error handling discipline. Several `try/catch` blocks are too broad and do swallow failures that should either surface or be recorded as degradations. `OleDbValueSampler.SafeCardinality` catches every exception and returns `0`, which means malformed SQL, bad identifier quoting, provider issues, or other scanner defects all collapse into a benign-looking cardinality value. `SampleValues` does the same thing: it returns a partial or empty sample for any exception, which is a reasonable fallback for a narrowly defined “unsampleable type” case but too broad for connection-level or SQL-construction failures. On the DAO side, `TryReadBoolProperty` and `TryReadStringProperty` catch all exceptions and return `null`; that is appropriate for a missing optional property like `RowSource`, but it also masks broader DAO/COM failures as though the property simply were not present. By contrast, the provider-probing catches in `BuildConnectionString` are meaningful, because that code is intentionally trying multiple providers. So the project is not over-catching everywhere, but the specific scanner catches you pointed out are indeed too blunt for “lean by default”.

6. Test coverage. The hermetic tests are solid for the pure logic that was isolated. `PiiDictionaryTests`, `ValueFormatDetectorTests`, `HeuristicsEngineTests`, and `ClassificationWriterTests` give good evidence that the core non-COM heuristics and the JSON writer behave as intended in many mainline cases, and `ClassificationWriterTests` does real schema validation against the committed schema. The integration test is also wired correctly to skip without Access: it uses `[SkippableFact]`, calls `AccessAvailability.SkipIfNoAccess()`, and additionally skips if `HomeHealthCare.accdb` is absent. So the skip mechanics look right.
   
   What the tests do not prove is the scanner’s behavior on the exact edge cases where the implementation is weakest. There is no test that lookup-table payload columns become `lookup-reference`; no test for `ReadLookupRowSource` resolving a bare table name to a real target PK column; no test for identifier escaping when a table or column name contains `]`; and no test that unsupported composite/implicit FK cases produce degradations. So I would rate the test suite as good for isolated logic, but not sufficient proof of the full scanner contract.

7. Anything else for orchestrator closeout. The file-layout deviation is acceptable: the spec named a `Pipeline` path, but the actual split into pipeline interfaces plus a COM implementation under `Core/Com` is a reasonable architectural refinement, not a defect. The more important note is SQL construction. `OleDbValueSampler` interpolates schema-derived table and column names into bracketed SQL without escaping closing brackets, so although this is not classic user-supplied input injection, it is still a robustness/security problem when scanning an untrusted database and can break or alter the query text. That becomes worse because the resulting exceptions are currently swallowed into `0` cardinality or empty samples. Also, the code advertises a `Degradations` channel and CLI exit code `3` for partial failure, but nothing currently populates that list, so promised degradation reporting is effectively unimplemented. That matters especially for composite FKs and unresolved implicit FKs, where the schema comments explicitly say the scanner should surface a degradation rather than pretend the metadata is authoritative.
