### 1. High-level interpretation

*   **`examples/minimal-form.json`**: This file is an `ir/Forms/*.ir.json` record representing a small Access form, confirmed by its `"Type": "Form"`, that has both VBA code in `VbaCode` and a structured representation of that code in the `Procedures` array, as well as an embedded macro described in `EventMacros`.
*   **`examples/complex-form.json`**: This file is an `ir/Forms/*.ir.json` record for a larger Access form, confirmed by `"Type": "Form"`, which is bound to a data source as shown by `"RecordSource": "tblServices"`, has a deep UI hierarchy in its `Children` array, and has multiple VBA event handlers indicated by properties like `"OnDirty": "[Event Procedure]"`.
*   **`examples/northwind-output.json`**: This file is a `manifest.json` envelope for a harvester run, confirmed by `"SchemaType": "DatabaseManifest"`, whose `Summary` shows zero objects and whose per-category arrays like `Forms` and `RowSourceSpecs` are empty, which the guide explains is an intentional normalization for the canonical corpus.

### 2. Per-record traversal

Walking `examples/complex-form.json` against the guide's §5.1 conventions:

*   **(a) `RecordSource`**: The form is bound to a table. The path is `$.Properties.RecordSource`, which has the value `"tblServices"`.
*   **(b) Enricher-added fields**: The guide promises `GeometryIn`, `Procedures`, and `NonDefaultProperties`. The record contains all three:
    *   `$.Procedures`: An array of 7 procedure objects extracted from the VBA code.
    *   `$.NonDefaultProperties`: An array of 4 property names that differ from Access defaults.
    *   `$.Children[0].Children[5].GeometryIn`: An object with `"H": 0.5`, representing the FormHeader's height in inches.
*   **(c) VBA event-binding**: The guide documents the `"[Event Procedure]"` pattern. An example in the record is `$.Properties.OnCurrent` with the value `"[Event Procedure]"`.
*   **(d) Control from `Children`**: The `Children` array contains the form's UI tree. An example control is a `TextBox` at path `$.Children[0].Children[6].Children[0].Children[2]`, whose name is `"txtServiceName"` (at `...Properties.Name`).

### 3. Gap detection

*   **Field:** `TextCapacity` object, present on many controls in `complex-form.json` (e.g., `...Children[0].Children[5].Children[0].Children[0].TextCapacity`).
    *   **What is missing:** The guide does not mention the `TextCapacity` object, its purpose, its sub-fields (`charsPerLine`, `visibleLines`, `font`, `metric`), or the meaning of its `{ "unavailable": true, ... }` state.
    *   **Impact:** Non-blocking, but adds ambiguity. A consumer performing UI analysis cannot use this potentially valuable enrichment without understanding its contract.
    *   **Needed addition:** A paragraph in §5.1 should document `TextCapacity` as an enricher-added field that provides an estimated text capacity for a control based on its geometry and font. It should define the sub-fields and explain that the `unavailable` state occurs when geometry is missing, preventing the calculation.

*   **Structural pattern:** The `Properties` bag contains many undocumented, hex-encoded fields beyond the examples given in §5.1 (e.g., `RecSrcDt`, `PrtMip`, `PrtDevModeW`, `PrtDevNamesW`).
    *   **What is missing:** The guide states that such properties "can be safely ignored," but it provides no context for what they are or when a consumer might *not* want to ignore them (e.g., for a high-fidelity migration).
    *   **Impact:** Non-blocking, but adds ambiguity. It forces a consumer to trust the "safe to ignore" advice without any means of verification.
    *   **Needed addition:** A short paragraph in §5.1 should state that the property bag is a direct dump from Access and includes many internal-use fields related to printer settings, GUIDs, and cached metadata. It could clarify that unless the consumer's goal is to replicate Access-specific behaviors like printer driver settings, these fields have no bearing on application logic, structure, or behavior.

*   **Field/Convention:** The casing of the `source` field in the `Label` object.
    *   **What is missing:** The guide's example in §7 uses `"Label": { "Source": "Attached", ... }` (PascalCase), while the `complex-form.json` example shows `"Label": { "source": "attached", ... }` (camelCase). The guide does not specify a casing convention or acknowledge this discrepancy.
    *   **Impact:** Non-blocking. A robust parser would likely use a case-insensitive comparison, but it is an inconsistency between the specification (guide) and the implementation (JSON output).
    *   **Needed addition:** The example in §7 of the guide should be corrected to match the actual JSON output (`"source": "attached"`) to remove the ambiguity.

*   **Structural pattern:** The omission of the `EventMacros` object.
    *   **What is missing:** `minimal-form.json` has an `EventMacros` object, but `complex-form.json` does not. The guide explains what omission means for properties (`null` vs. omission in §7.1), but not for top-level enrichment objects. It's implied that `EventMacros` is omitted if there are no embedded macros, but this is not stated explicitly.
    *   **Impact:** Non-blocking, but adds ambiguity. A consumer must infer the meaning of the object's absence.
    *   **Needed addition:** A sentence in the description of `EventMacros` in §5.1 should explicitly state: "This object is omitted from the form record if the form contains no embedded UI macros."

*   **Convention:** The canonical filename for the manifest.
    *   **What is missing:** The guide refers to the manifest file as `manifest.json` throughout the text and provides an example named `northwind-output.json`. It never explicitly states that a harvester run *always* produces a file at the root named `manifest.json`.
    *   **Impact:** Non-blocking. It is a very strong implication, but a consumer wanting a deterministic entry point would prefer an explicit statement.
    *   **Needed addition:** A sentence in §2 ("What the harvester produces") should state: "Every run produces a `manifest.json` file in the root of the output directory."

### 4. Overall verdict

**SUFFICIENT WITH ADDITIONS**. The guide is well-structured and provides the necessary concepts to interpret the core structure and relationships within the harvester output. A consumer can successfully follow the "reading order," join data across files using the specified keys, and understand the key conventions like `null` vs. omission. The identified gaps, particularly the undocumented `TextCapacity` object, are notable omissions but do not fundamentally block the interpretation of data flow, UI structure, or application logic. With the specific additions detailed above, the guide would be fully sufficient.
