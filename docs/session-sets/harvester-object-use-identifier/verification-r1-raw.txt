### 1. Taxonomy completeness

The seven-category taxonomy (`MainDataEntry`, `LookupReference`, `Reporting`, `NavigationShell`, `StandaloneUtility`, `PossiblyUnused`, `Unknown`) is robust and covers the most common usage patterns for Access objects in business applications. The categories are well-defined, mutually exclusive, and address the primary roles of forms, reports, tables, and queries. The inclusion of `PossiblyUnused` and `Unknown` provides necessary fallbacks for unreferenced objects and ambiguous cases.

However, a notable gap exists: the taxonomy and classification rules do not explicitly account for **Action Queries** (e.g., `UPDATE`, `INSERT INTO`, `DELETE`, `MAKE TABLE`). These are a fundamental component of many Access applications, used for batch data processing, and represent a distinct usage pattern from `SELECT` queries (data retrieval/reporting) or `Crosstab` queries. In the current design, an Action Query would likely be classified as `StandaloneUtility` or `PossiblyUnused` if not called directly from a UI object, failing to capture its data-modifying intent.

### 2. Signal collector feasibility

The six described signal collectors are feasible and correctly designed to operate on the specified KB/IR file structure without requiring Access COM automation. The extraction logic for each is sound:
- **RecordSource/RowSource:** Reading `Properties.RecordSource` and `Properties.RowSource` from form/report IR JSON is a direct and reliable method.
- **NavigationGraph/VbaReference:** Using regex to parse VBA code for `DoCmd.Open*`, domain functions (`DLookup`, etc.), and `OpenRecordset` calls is a standard static analysis technique. While it cannot capture dynamically constructed object names, it is sufficient for a baseline implementation. Similarly, parsing macro IR for `Open*` actions is straightforward.
- **QueryTableReference:** Parsing the `Sql` field from query IR files using regex for `FROM` and `JOIN` clauses is a practical, though imperfect, approach to discovering table dependencies.
- **RelationshipGraph:** Reading pre-processed relationship files is the most reliable way to determine foreign key structures.

All specified sources and extraction methods align with the expected output of the harvester, making the signal collection strategy viable.

### 3. Classification rule correctness

The classification rules are logical and correctly handle canonical cases. The "first matching rule wins" approach provides a deterministic classification process. For example:
- A form with a `RecordSource` pointing to a transactional table and containing CRUD event handlers will correctly match rule F1 and be classified as `MainDataEntry`.
- A form lacking a `RecordSource` but containing navigation commands (`DoCmd.OpenForm`) will correctly match rule F5 and be classified as `NavigationShell`.
- A table named `tlkpStates` or having few columns and no foreign key children will correctly match rules T3/T4 and be classified as `LookupReference`.
- A report with any `RecordSource` will correctly match rule R1 and be classified as `Reporting`.

The rules demonstrate a clear hierarchy from high-confidence, specific patterns to more general ones, which is a sound design.
