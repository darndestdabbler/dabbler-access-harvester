1. **F4 fix: query RecordSource vs. table RecordSource**

The F4 change is logically correct. Before the fix, the branch effectively treated any non-transactional, non-lookup RecordSource as if it were a query-backed reporting form. The new `index.KnownQueryNames.Contains(rs)` guard closes that hole by making the F4 path contingent on the RecordSource actually being a known saved query. That is the right discriminator for the specific Round 1 failure mode.

`Form_PlainTable_RecordSource_No_FK_Is_MainDataEntry` is also a meaningful regression test, assuming the test data does what its name implies: the RecordSource is a real table name, there are no FK-child signals, and the name does not trip the lookup heuristic. In that setup, the old bug would have classified the form as `Reporting`; the new logic should classify it as `MainDataEntry` at low confidence. That directly exercises the corrected branch boundary. Paired with `Form_Query_RecordSource_Is_Reporting`, the two tests cover both sides of the decision point and are good regression protection for the original bug.

One small observation: if you want the regression to be tighter, asserting confidence as well as category would make it harder for a future refactor to silently collapse the two paths again. But category-level coverage is already meaningful and does cover the failure mode.

2. **Module/Macro classification paths and objectType schema risk**

The new Module/Macro paths are reasonable as a pragmatic extension of the taxonomy. Even though the written strategy rules were originally defined for Forms, Reports, Queries, and Tables, `StandaloneUtility` and `NavigationShell` are category labels that naturally generalize to modules and macros. A VBA module with code and no stronger signals fitting `StandaloneUtility`, and a macro that opens forms fitting `NavigationShell`, are both sensible choices.

On the implementation side, I do not see a classification-design problem with emitting findings for those object kinds. In fact, given the top-level `Classify` contract is “one finding per object,” adding them is better than silently omitting them.

The only real risk here is **external contract/schema alignment**, not classifier logic. If `UsageFinding.ObjectType` is validated elsewhere by a fixed enum that only allows `"Form"`, `"Report"`, `"Query"`, and `"Table"`, then `"Module"` and `"Macro"` would be a downstream compliance issue. Nothing in the provided snippets proves that such a restrictive schema exists, so I would not fail this round on that basis alone. But it is worth confirming that any JSON schema, API contract, docs, or consumer-side enum has been updated consistently.

3. **`SqlDetection.IsInlineSql` and the word-boundary requirement**

The boundary logic is correct for the requirement you called out. The helper first checks `StartsWith(prefix, OrdinalIgnoreCase)`, then verifies that the next character is either absent or not an identifier character (`letter`, `digit`, or `_`). That means:

- `"Selected"` does **not** match `SELECT`
- `"Withholding"` does **not** match `WITH`
- `"ParametersX"` does **not** match `PARAMETERS`
- `"DELETE_ME"` does **not** match `DELETE`

while these do match correctly:

- `"SELECT * FROM tblX"`
- `"PARAMETERS p Text; SELECT ..."`
- `"CREATE TABLE ..."`
- `"UPDATE tblX SET ..."`

So for the stated false-positive class, the implementation is good.

The boolean expression is also logically fine as written because `&&` binds tighter than `||`. I would still parenthesize it for readability, but that is clarity, not correctness.

The only thing missing from what you showed is explicit unit coverage for these boundary cases. I do not see a logic bug; I just do not see regression tests for it yet.

4. **Remaining material gaps affecting the Session 3 pilot**

Yes — there is still one material gap, and it is independent of the Round 1 fixes:

**inline SQL RecordSources are being excluded from the named-object index, but the classifier is also using that same index to decide whether a form/report has a RecordSource at all.**

Concretely:

- `RecordSourceCollector` intentionally omits inline SQL
- `SignalIndex.RecordSourceByObject` is built from that collector
- `ClassifyForm` determines `hasRecordSource` via `index.RecordSourceByObject.TryGetValue(...)`

That means a form whose `RecordSource` is inline SQL, such as `SELECT * FROM tblClients`, is treated as if it has **no RecordSource**. Such a form will skip the F1–F4 bound-form logic entirely and fall into F5/F6/F7 depending on nav edges and VBA presence. That is a real misclassification risk for bound forms and reports that use inline SQL instead of a saved query or table name.

This also has a second-order effect: tables or queries referenced only inside inline SQL RecordSources are invisible to the current cross-reference signals, so they can be undercounted or pushed toward `PossiblyUnused`.

That gap is material for Session 3 if the pilot databases use inline SQL RecordSources with any frequency. The right fix is to separate:

- **“this form/report is bound”** from
- **“this form/report names a saved table/query object as its RecordSource”**

Use the raw non-empty `form.RecordSource` / `report.RecordSource` to determine bound status, and keep the named-object index for reference tracking. Ideally, inline SQL should also be parsed for underlying table/query references using the same kind of extraction logic you already apply to saved queries.
