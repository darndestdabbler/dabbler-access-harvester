1. **(S2-2/H2) `BuildModuleItem` uses a failure-scoped catch instead of a pre-emptive `HasErrorNode` scan.**  
This change is sound and, in practice, better than the literal pre-scan. A pre-emptive `HasErrorNode(item)` gate would eagerly downgrade any recovered item, including partially valid procedures whose AST can still be built usefully. The shipped shape instead only degrades when two things are true: the subtree is already known to be recovery-tainted, and the exception is one of the expected structural-fault classes (`NullReferenceException`, `IndexOutOfRangeException`, `ArgumentOutOfRangeException`, `InvalidOperationException`). That is the right tradeoff for Session 2: it preserves recoverable content while still preventing one mangled item from detonating the entire module build. The remaining blind spot is recovery that produces a malformed tree *without* an error node; but that blind spot also exists in the literal pre-scan design, so this deviation does not introduce a new failure mode. I do not see it as hiding a real builder bug inappropriately; genuine non-recovery faults still escape.

2. **(S2-1/H1) `contextualKeywordName` admitted into `primary` and variable-class name slots.**  
This is also sound. The chosen keywords are only special in tightly anchored syntactic positions: `STEP` after a `For ... To` bound, `PRESERVE` after `ReDim`, `COMPARE`/`EXPLICIT` after `Option`, and `LIB`/`ALIAS` inside `Declare`. Re-admitting them in bare expression position (`primary`) and in variable-class declaration/name slots matches real VBA’s contextual behavior. The pinned anchored cases are the right ones to test, and the grammar shape supports the claimed behavior: the anchored productions are structurally stronger than the generic identifier uses, so ANTLR can still prefer `ReDim Preserve ...`, `Option Compare ...`, `Declare ... Lib ... Alias ...`, and `For ... Step ...` when those forms are syntactically complete. I do not see a meaningful ambiguity or harmful over-acceptance in the admitted slots. The main boundary here is not over-acceptance; it is the deliberate *under*-acceptance of some other identifier slots, which is addressed separately in concern 5.

3. **(H4) suffixed `Function`/`Property Get` names now populate `ReturnType` from the suffix while retaining `TypeSuffix`.**  
This is the right implementation. In legacy VBA, the suffix on a function/property-get name is semantically the return type. Stripping the name for resolution but then leaving `ReturnType` null would preserve spelling while losing meaning; that would be an incomplete F-3-2 fix. Using the existing `ReturnType` channel avoids a schema expansion, and retaining `TypeSuffix` preserves source fidelity. The precedence rule is also correct: an explicit `As ...` should win if present, while the raw suffix remains available for later validation or fidelity-sensitive consumers. That is better than the rejected alternative of dropping `TypeSuffix` and synthesizing only a type reference. The documented `!` limitation is separate and correctly treated as a lexer/grammar ambiguity, not a semantic issue with the suffix-to-type mapping itself.

4. **(H3) `namedArgument` now accepts `contextualKeywordName`.**  
Correct, and necessary. Once `step`/`compare`/etc. are legal parameter names, the corresponding named-argument call syntax must accept the same token class or the grammar becomes self-inconsistent. The fix is narrow and safe because `:=` cleanly disambiguates a named argument from an expression. This closes a real hole created by the F-3-2 broadening and matches VBA behavior.

5. **Deferred gaps: `!`-suffixed function/property names (DW-4) and other contextual-keyword slots (DW-1).**  
`DW-4` is acceptable for Session 2. The `!` case is a genuine lexer/parse ambiguity around `BANG`, it is documented, and it is absent from both cited corpora. I would not block the session on that deferral. `DW-1` is the closest thing to a literal scope shortfall, because the broadest reading of “contextual keywords ... as identifiers” could include procedure names, type/enum members, labels, and declare-name slots. That said, the narrowing is explicit, documented, and fenced with tests so it cannot silently masquerade as full coverage. Given the evidence provided, the lack of corpus impact, and the fact that the implemented slots cover the actual parser-failure chain that changed the HHC golden, I accept this as an intentional scope line rather than a hidden defect. If someone wanted a stricter reading of the session brief, this is the only area I would revisit; I do not consider it blocking here.
